Building an HTTP Server the Hard Way

An HTTP/1.1 server written from raw TCP sockets — no Express, no framework in between. What I set out to learn, and what the wire taught me back.

By Great Ezenna Node.js · TypeScript Filed under: Systems Read the source →

I did not build this because the world needed another web server. I built it because I wanted to know what happens under the frameworks I use every day — what an HTTP request actually is once you strip away everything that hides it. So I opened Node's net module, gave myself a raw TCP socket, and nothing else.

The rule I set was simple: no framework in between. The server listens on a socket, reads bytes off the wire, and turns them into something meaningful entirely by hand. It parses the request line and headers with regular expressions, splits the path from its query string, decodes JSON and form-encoded bodies, and writes a valid HTTP/1.1 response back out — status line, headers, blank line, body — byte by byte.

The lesson that arrives in pieces

The thing that surprised me most was also the most fundamental: TCP does not hand you a whole message. I had quietly assumed that one request would arrive as one neat chunk of data. It doesn't. A socket is a stream of bytes, and those bytes arrive whenever the network feels like delivering them — a header here, half a body there, the rest a moment later.

So the server can't just react to every data event as if it were complete. It has to buffer what it's received and keep asking a quieter question: do I have a whole request yet? For now I answer that by watching for the \r\n\r\n that marks the end of the headers before I try to parse anything. Getting that wrong means replying to half a request — and getting it right is the difference between reading a protocol and merely reading about one.

Building it like Node builds it

I could have kept the interface primitive — pass strings around, be done with it. Instead I modeled it on Node's own http module. The request object extends Readable, the response extends Writable, and the server is an EventEmitter that emits a request event — so you can write server.on("request", (req, res) => …) exactly the way you would with the real thing.

That was deliberate. I wanted to learn the actual interface — the shape professional tools present to you — not a toy version of it. And, honestly, I liked it. There is a particular satisfaction in calling res.setHeader() and res.write() on something you built from a bare socket, and having it behave the way the library you copied does.

What the wire made me handle

Working this close to the protocol turns abstractions back into problems you can see. A client can send an enormous body, so the server tracks the total bytes received and answers oversized requests with 413 Payload Too Large instead of swallowing them. A connection might ask to stay open or to close, so it reads the Connection header and honours keep-alive or hangs up accordingly. A browser can vanish mid-request, so it catches ECONNRESET and treats a disappearing client as ordinary, not exceptional.

Where it stands

I consider this done — as a learning artifact. It parses requests, routes methods, reads bodies and query strings, and writes correct responses, and along the way it taught me the thing I came for. I keep an honest checklist of what a production-grade server would still need: framing bodies by Content-Length rather than trusting \r\n\r\n, chunked transfer encoding, stricter connection handling. I may come back and work through it. I may not. Either way, I no longer use a web framework without a picture of what it's doing on my behalf — and that was always the point.
